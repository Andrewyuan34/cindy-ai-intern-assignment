# B1：做出来

## 1. 做了什么？

我使用 Codex 协助完成了一个 Cindy PR 看板插件，并通过 Cindy Forge 打包安装。插件提供“我创建的”和“待我评审”两个列表，展示未关闭 PR 及当前提交的 CI 状态。点击“分析 CI”后，AI 在该 PR 对应的独立任务中接手；之后可以查看诊断，或在同一任务中重新分析。 [源码与使用说明](https://github.com/Andrewyuan34/cindy-ai-intern-assignment/tree/main/plugins/pr-dashboard)

在开始实现前，我先让 Agent 阅读项目、调查已有插件能力，并在说明背景和选项后与我确认方案。我们提前讨论了入口形式、GitHub 登录、刷新方式以及 AI 任务如何组织，最终确定常驻面板、复用 gh 登录并提供备用 PAT、每个 PR 使用独立诊断任务。刷新方式也经过讨论，最终选择打开面板、返回前台和手动触发，不引入 GitHub 推送接收服务。

## 2. 卡在哪？

从我指挥和验收的角度，这次没有遇到明显需要推翻方案的功能性阻塞。前期已经把主要使用流程和 GitHub 协同方式讨论得比较具体，Agent 可以沿着这些确定的要求实现。

需要进一步调整的是界面效果。看到首版后，我觉得它不够美观，信息呈现也不够简洁。回看前期沟通，我们明确了功能，却没有同样具体地约定视觉风格和设计语言。因此，这次调整主要是在补齐设计要求。

验收时还有一个实际条件限制：当时已有的 PR 缺少可读取的 CI 检查，无法直接用来验证失败诊断流程。因此，我选择在答题仓库创建一个专用验收 PR。

## 3. 怎么检查、怎么解决？

对界面问题，我提供了参考图片，要求 Agent 调查相关设计方法和图标方案，再把“简洁、突出重点”落实成具体要求：优先展示 PR 标题和 CI 状态，弱化仓库名、编号和更新时间，删掉重复说明，每条 PR 保留一个主操作，把次要操作放进“更多”菜单。经过示意效果确认后，再修改实际插件并检查运行效果。

对功能，我通过专用验收 PR 检查完整流程：先构造一次失败的 CI，让 AI 根据失败信息分析原因；随后修复样本，确认 CI 通过、看板状态更新，并验证重新分析仍使用原诊断任务。这里的失败是专门设计的验收样本，不是插件自身发生的故障。

实现、测试和具体调试由 Agent 执行，我主要负责明确目标、判断方案取舍、审阅结果和提出调整要求。源码、运行截图及验证记录已经提交到 GitHub；记录中区分了真实 Cindy 验收和本地模拟检查。 [运行截图与验证记录](https://github.com/Andrewyuan34/cindy-ai-intern-assignment/blob/main/plugins/pr-dashboard/IMPLEMENTATION.md)
