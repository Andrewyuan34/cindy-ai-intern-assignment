# 收工检查

按以下四步实际执行。只检查和报告，任何修改须先获用户确认；不自行提交、推送或发布，也不默认调用会推动来源任务修复的 Cindy `/review`。

## 准备

- 确认工作目录，读取项目及相关模块的 AGENTS.md。Cindy 源码仓按需读取 `docs/dev-rules/development-workflow.md` 的提交前验证，以及 `docs/dev-rules/engineering-conventions.md` 的日志规范与 Review 清单。复用上下文中已读且有效的规则，不重复通读。
- 根据任务记录确认基线，区分已有工作，列全本次已提交、暂存、未暂存和新增文件；基线或改动归属不清时先询问用户，不默认用 HEAD 或 main。

## 1. 跑测试

按项目约定，在正确目录实际运行本次相关测试及必要检查，等待结束并核对覆盖范围。入口不明时查实际脚本和 CI 配置，仍无法确定则询问。

Cindy 默认使用 `pnpm test:unit:related` 加受影响包的类型检查；纯说明文档按项目规则运行 `pnpm check:dev-docs` 等检查，不强制全仓测试。

命令不得夹带自动修复或快照更新；没有纯检查入口时先问。失败或阻塞仍继续后续审阅。构建成功、零测试、全部跳过均不能写成测试通过，不得弱化测试制造通过。

## 2. 完整审阅改动

逐文件读完全部差异和必要上下文；新增文本读全文，删除、重命名检查关联影响，非文本用相应工具检查。对照需求和项目清单判断逻辑、边界及遗漏，不能只看 diff 统计。无法检查的内容列为未验证。

## 3. 排查调试残留

在变更文件中搜索 `console.log`、`debugger`、临时打印等线索，结合上下文检查写死测试值、假接口和绕过逻辑。按项目规范区分正式日志、合理常量及测试 fixture；搜索无命中不代替完整审阅。发现或存疑项只记录，不直接修改。

## 4. 简短汇总

固定报告：
- 范围：任务基线和覆盖范围。
- 摘要：1–3 条说明改了什么。
- 测试：实际命令、退出状态和关键结果，区分通过、失败、未运行、未完成；超时或中断不能算通过。
- 发现：文件位置、依据、影响和建议；无发现也明确说明。
- 未验证与待确认：遗漏、阻塞和需要授权的修改；没有则写“无”。

结论须对应当前内容；检查后若有新改动，补审差异并重跑受影响测试。未解决问题不能视为已完成，不确定判断须注明。
